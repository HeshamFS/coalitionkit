# Scorecard, 30 October 2026

The first public scorecard of CoalitionKit Core v0.1: all eight acceptance tests, run against the live models where a test uses a model, on one Windows 11 workstation (Python 3.15.2, SQLite and PostgreSQL 18 in Docker).

Agents ran on Muse Spark 1.3 (contributor tier) through the Meta API. The Steward's model audit ran on Muse Spark Open on Baseten. Re-run everything with:

```sh
COALITIONKIT_LIVE=1 COALITIONKIT_ACCEPTANCE_FULL=1 uv run python -m coalitionkit_acceptance.scorecard
```

Without keys, the same command runs every scripted part and lists each live part as not run, with the reason.

## Conformance

The published runner checked the reference host at the host level with keys configured (`coalitionkit conform --level host --operator reference`): 9 of the 10 host tests pass (C-09 to C-16 and C-20). C-21 did not run: a member cannot yet observe whether an offer is counted before it accepts a new charter revision. The signed report is [docs/conformance/reference-host-2026-10-30.json](../conformance/reference-host-2026-10-30.json).

## Live round trip on WhatsApp

A real phone was linked to a member with a one-time code through the published Meta app. An option reply opened the confirm step with a single-use code, free text was refused and signed nothing, and a note scoped to organizers never reached the phone.

## Not covered

- **Test 8, exact match.** The provider's export cannot be filtered to the acceptance key from the account used, so the exact per-key comparison did not run. Only the upper bound did.
- **Notes on WhatsApp.** The message door sends a member's decisions, questions and tasks. Plain notes are not part of that view yet.
- **Test 6 variance.** The attack suite includes cases the Steward model writes, so a run can differ. One full run had a case the server refused with the MCP library's validation text instead of a policy code; that was fixed and the two runs above passed.
